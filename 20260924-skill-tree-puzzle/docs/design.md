# 設計ドキュメント

スキルツリー・パズルの設計の前提と、判断の理由をまとめる。開発者向け。
遊び方・ルールは [README](../README.md) を、型の定義は [`src/types.d.ts`](../src/types.d.ts) を参照する。

## 1. 目的と前提

取捨選択・経路の計画・シナジーの発見を、詰将棋のように考えて解くパズルにする。
そのために、次の2つを崩さない。

- **乱数を使わない。** 同じビルドとお題なら、必ず同じ結果になる
- **勝敗は、取得したノードの集合だけで決まる。** 取得した順番は結果に効かない。
  順番に意味がある周期スキルも、ツリーの定義順に並べて回す（[5. ローテーション](#5-ローテーション)）

この2つがあるので、配布 pt で組めるビルドを総当たりすれば、お題の解をすべて確かめられる（[6. お題の設計と検証](#6-お題の設計と検証)）。

## 2. 全体構成

| ディレクトリ | 役割 |
| --- | --- |
| `src/core/` | 判定。取得・解除の可否、ビルドの列挙、保存の読み書き、戦闘。DOM に触らない |
| `src/data/` | キャラの一覧（`characters.js`）と、キャラごとのツリー・お題の定数（`<キャラID>/`） |
| `src/ui/` | 描画とタップの通知。判定を持たない |
| `src/main.js` | 選んだキャラ・お題と取得済みノードを状態として持ち、判定と描画を繋ぐ |
| `src/storage.js` | ブラウザへの保存（localStorage）の読み書き。`main.js` だけが使う |

ファイル単位では次のとおり。各ファイルの先頭のコメントにも、同じ役割を書いている。

```text
src/
├── main.js      # 入口。状態を持ち、判定と描画を繋ぐ
├── storage.js   # 保存キーの命名と、選んだキャラ・お題・ビルド・クリアの記録の読み書き
├── types.d.ts   # 型の定義
├── core/
│   ├── profile.js         # ビルド・敵の能力を、戦う側ごとの集計（CombatantProfile）にまとめる
│   ├── simulate.js        # ビルドと敵1体の戦闘を1ターンずつ進め、ログと勝敗を返す
│   ├── challenge.js       # お題単位の判定（独立戦・連戦・戦う順番の総当たり・クリア判定）
│   ├── clear-record.js    # 画面でのクリアの判定と、クリアの記録（自己ベスト）・最少 pt の開示・★の判定
│   ├── build.js           # ツリーの隣接と、ノードを取得・解除できるかの判定
│   ├── enumerate.js       # 配布 pt で組めるビルドの列挙と、総当たりでの最少クリア pt
│   ├── saved-build.js     # 保存するビルドの書き出しと、今のツリーで組めるかの確認
│   ├── ability-table.js   # 能力の表（語・日本語名・規定値・Effect の作り方）
│   └── parse-abilities.js # デバッグ入力の文字列を Effect の配列にする
├── data/
│   ├── characters.js      # キャラの一覧（ID・名前・ツリー・お題）
│   └── warrior/           # 戦士
│       ├── tree.js        # スキルツリー
│       └── challenges.js  # お題（敵の組と配布 pt）
└── ui/
    ├── tree-view.js       # ツリーの描画とタップの通知
    ├── panel.js           # キャラとお題の選択・お題の記録・お題の情報とボスの能力のバッジ・残り pt・ボタン・連戦の相手選び
    ├── log-view.js        # 戦闘ログと結果の表示。敵が複数なら敵ごとに切り替える
    ├── debug-input.js     # デバッグ入力の欄とボタン
    ├── build-stats.js     # 組んだビルドのステータスと能力のバッジの表示
    ├── description-popover.js # 能力やノードの説明の吹き出しと、能力のバッジ
    ├── ability-names.js   # 能力・攻撃・報酬の表示と、能力のバッジ名・説明、ノードの説明
    └── element-names.js   # 属性の表示名
```

依存は `main.js` → `storage.js` / `ui` / `core` / `data`、`storage.js` → `core`、`ui` → `core`、`data` → `core` の一方向にする。
`core` の戦闘まわりは `challenge.js` → `simulate.js` → `profile.js` の順に依存する。
`data` が `core` を使うのは、ツリーのノードを能力の表（`core/ability-table.js`）から作るため。
`core` は `ui` を知らないので、`node --test` と `scripts/verify.js` から DOM 無しで動かせる。

表示と判定で、同じ集計を使う。
ビルドのステータス表示（`ui/build-stats.js`）とお題のボスの表示（`ui/panel.js`）は、
勝敗の判定と同じ `createProfile` / `createEnemyProfile`（`core/profile.js`）から作る。
計算を二重に書くと、画面の数値とログの結果がずれるため。

## 3. 戦闘モデル

戦闘は `core/simulate.js` の `simulate` が、ビルドと敵1体から決める。

### 1ターンの流れ

1. ターン開始：味方、敵の順に再生する
2. 味方の行動
3. 敵の行動
4. ターン終了：味方、敵の順に毒を与える

どの段階も味方が先に動く。どこかでどちらかの HP が0になった時点で、戦闘を終える。

行動では、ローテーションで今のターンの属性を決め、連撃の回数だけ通常攻撃する。
1発当てるごとに、相手が反撃を持っていれば反撃を受ける。

### 1発のダメージ

次の順で計算する。

1. `今の攻撃 × ratio × (1 − 相手の軽減率) × 倍率` を求める。
   今の攻撃は、逆上で上がった分を含む。
   倍率は、背水・好機・周期スキル（溜め・解放）の倍率をすべて掛けたもの
2. 小数を切り捨てる。誤差で1つ下がらないよう、`FLOAT_TOLERANCE` を足してから切り捨てる
3. 相手の今の防御を引く。0 未満なら0。今の防御は、破甲で下がった分を含み、0 未満にはならない。
   攻撃側が貫通を持っていれば引かない

条件（背水）の倍率は1発ごとに、その時点の自分の HP で判定する。
反撃で HP が減ると、同じターンの次の1発から倍率が掛かる。
逆上も同じで、反撃を受けて攻撃が上がると、同じターンの次の1発から効く。

反撃は固定ダメージで、倍率は掛からない。防御は通常攻撃と同じく引く（破甲・貫通も効く）。

### 攻撃を当てた・受けたとき

吸収・逆上・破甲・刻印は、攻撃を当てた・受けた直後に起きる。
契機になる攻撃は、通常攻撃の1発と反撃で、毒は含めない。
反撃は相手の攻撃で、毒は状態によるスリップダメージとして分ける。
処理は `strike` にまとめ、通常攻撃と反撃の両方がここを通る。

- 倒した1発では、戦闘が終わるので状態を変えない
- 逆上・破甲・刻印で変わった値は、行を増やさないよう、攻撃のログの `changes` に添える。
  吸収の回復は、別のログにする
- 好機の倍率は、掛かったターンだけ通常攻撃のログの `tempo` に持たせ、攻撃の行に添える
- 戦闘中に変わる値（逆上で上がった攻撃・破甲で下がった防御・付いた刻印）は `Fighter` に持ち、`CombatantProfile` は書き換えない

HP を減らす処理は、攻撃・反撃・毒のどれも `takeDamage` を通す。
致死時の能力（食いしばり）を1か所で扱うため。

### 勝敗

- 敵の HP を0にすれば勝ち
- 味方の HP が0になれば負け（`defeated`）
- ターン上限を終えても敵が残っていれば負け（`turnLimit`）

お題に敵が複数いるときは、お題の `mode` で扱いが変わる。
どちらも、戦うたびに味方の HP と食いしばりは満タンから始まる。

- **`independent`（省略時）：** 同じビルドで1体ずつ独立に戦い、すべてに勝てばクリアにする
- **`sequence`（連戦）：** 敵を1体ずつ好きな順に倒す。
  倒した敵の `reward`（`Effect` の配列）を、ビルドの後ろに足して次の敵と戦う。
  ある順番で全員に勝てればクリアにする。
  持ち越すのは報酬だけで、報酬は `createProfile(build, rewards)` が `applyEffect` を通して集計する

## 4. 能力

能力（`Effect`）は、ツリーのノードと敵が同じ定義で持つ。
戦う側ごとに `applyEffect` で `CombatantProfile` に集計し、戦闘はその集計だけを見る。
フィールドの一覧は `src/types.d.ts` の `Effect` と `CombatantProfile` を見る。

| 種類 | 集計のされ方 | 割り込む場所 |
| --- | --- | --- |
| `stat` | HP・攻撃・防御に足す | 集計時のみ |
| `multiHit` | 回数と ratio をそれぞれ掛ける（重ねがけできる） | 行動 |
| `conditional` | 一覧に足す。条件を満たす倍率はすべて掛かる | 1発ごと |
| `tempo`（好機） | 一覧に足す。条件を満たす倍率はすべて掛かる | 1発ごと（ターン数が every の倍数のとき） |
| `element` | ローテーションの末尾に足す | 行動の最初 |
| `charge`（溜め） | ローテーションの末尾に足す | 行動の最初 |
| `burst`（解放） | ローテーションの末尾に足す | 行動の最初。相手の刻印を全部使う |
| `counter` | ダメージを足す | 被弾するたび |
| `drain`（吸収） | 割合を足す | 攻撃を当てた直後 |
| `rage`（逆上） | 上がる量を足す | 攻撃を受けた直後 |
| `pierce`（貫通） | 持っているかどうか | 1発ごと・反撃 |
| `armorBreak`（破甲） | 下げる量を足す | 攻撃を当てた直後 |
| `mark`（刻印） | 付ける数を足す | 攻撃を当てた直後 |
| `regen` | 回復量を足す | ターン開始 |
| `poison` | ダメージを足す。防御を無視する | ターン終了 |
| `endure` | 持っているかどうか | HP が0になるとき（戦闘中に1回だけ） |

### 新しい能力を足す手順

1. `src/types.d.ts` に型を足し、`Effect` の union と、必要なら `CombatantProfile` のフィールドに加える
2. `core/profile.js` の `emptyProfile` に初期値を、`applyEffect` に集計を足す
3. `core/simulate.js` で、能力が割り込む場所に処理を足す。HP を減らすなら `takeDamage` を通す。
   攻撃を当てた・受けたときの能力なら `strike` に足す
4. ログに出すなら、`LogEntry` に種類を足し、`ui/log-view.js` で文章にする
5. `ui/ability-names.js` に表示を足す。`formatAbility` は報酬の一覧での名前、`formatBadgeLabel` はバッジの名前、`describeEffect` は効き方の説明。
   `CombatantProfile` にフィールドを足したときは、バッジに並べるよう `profileEffects` にも足す。
   説明は、ノードのタップと、自分・ボスの能力のバッジのタップで出る
6. `core/ability-table.js` の `ABILITIES` に1行足す（入力の語・日本語名・引数の規定値・`Effect` を返す関数）。
   デバッグ入力のボタン・パーサーの規定値と、ツリーのノードの効果・表示名がこの行から作られる。
   引数に範囲の制約があれば `check` に書く
7. `tests/simulate.test.js` にテストを足す

手順 5 の足し忘れは、`formatAbility`・`formatBadgeLabel`・`describeEffect` の戻り値が足りなくなるので `tsc` で分かる。
`profileEffects` の足し忘れも型検査では分からないので、`tests/build-stats.test.js` にテストを足して確かめる。
手順 2 の `applyEffect` は戻り値を持たず、足し忘れても型検査では分からないので、テストで確かめる。
手順 6 の足し忘れは、ツリーのノードで使えば読み込み時の例外で分かる。使わなければ、デバッグ入力で指定できないだけになる。

ノードに能力を置くときは、`data/<キャラID>/tree.js` の定義に `['英語名', 引数…]` を書く。
引数を省くと表の規定値になる。効果と表示名は表から作るので、ノード側には書かない。

## 5. ローテーション

属性攻撃・溜め・解放は、1ターンに1つずつ順番に使う周期スキルとして扱う。
周期スキルを発動してから、通常攻撃をする。溜めと解放のターンは、物理で殴る。

- **追加型。** 周期スキルを取るほど、1周が長くなる。得意な属性を足しても、その属性が回ってくる頻度は下がる。
  全部取るのが正解にならず、取捨選択が生まれる
- **定義順。** 味方はツリーの定義順、敵は `abilities` の並び順で回す。
  取得順で回すと、同じノードの集合でも結果が変わり、[1. 目的と前提](#1-目的と前提)が崩れる。
  そのため `main.js` と `scripts/verify.js` は、ビルドをそのキャラの `tree.nodes` の順に並べ直してから渡す
- **効果値は固定。** 周期スキルの数で効果値を変えない。
  ただし溜めの倍率は経過ターン数で、解放の倍率は相手の刻印の数で決まる（下の節）
- **効果はそのターンだけ。** 次のターンへ持ち越さない

周期スキルを1つも持たなければ、毎ターン物理で殴る。

### 溜めと解放

- **溜め：** 倍率は `1 + perTurn × 経過ターン数`。
  経過ターン数は前回の発動から数え、初回は戦闘開始から数える。
  t ターン目に回ってくる溜めでは `min(t, L)` になる（L は周期スキルの数）。
  周期スキルを増やすと、溜めが回ってくる頻度は下がる代わりに、1回の倍率が上がる。
  式だけで決まるので、戦闘中の状態を持たない
- **解放：** 回ってきたターンの初めに、相手の刻印を全部使う。倍率は `1 + perMark × 使った数`。
  刻印は `Fighter` に持ち、付けるのは刻印（`mark`）の能力

## 6. お題の設計と検証

### `verify.js` の読み方

```bash
node 20260924-skill-tree-puzzle/scripts/verify.js
```

お題ごとに、配布 pt で組めるビルドをすべて列挙し、`clearsChallenge` で判定して次を出す。

- 列挙したビルドの件数と時間
- クリアできるビルドの件数
- 最少クリア pt と、その pt での解（起点を除いたノード ID）
- 路線と、路線ごとの最少 pt・件数。「路線が2つ以上」「能力を共有しない2路線がある」の判定。
  判定は出力するだけで、終了コードには反映しない

**路線**は、クリアできるビルドを、取った能力ノード（ステータス以外の効果を持つノード）の組でまとめたもののうち、
他にクリアできる組を部分集合に持たない組を指す。
ステータスだけでクリアできるお題は、空の組がすべての組の部分集合になるので、路線が1つになる。
路線の最少 pt は、その組をちょうど取ったビルドの最少 pt で、ほかの能力を足したビルドは数えない。

起点だけのビルドは必ず列挙されるので、列挙が0件なら列挙のバグとして終了コード1で終える。
列挙はできてクリアが0件なら、お題が解けないことを表す。この2つを混同しない。

連戦のお題では、`clearsChallenge` が全順列（3体で6通り）を試すので、次の判定も出す。
仮の数値の間は判定を出力するだけで、終了コードには反映しない。

- 各敵が、報酬なしで単体のお題として倒せる
- 報酬なしで全員に勝てるビルドが、配布 pt 内に無い
- 最少 pt の解ごとの、勝てる順番。順番がビルドの型で分かれているかを見る
- どの順番でも勝てるビルドの件数。少数が望ましい

### 調整の目標

クリアは易しく、最少 pt で解き直すのをやり込みにする。

- 各お題を、複数の路線でクリアできるようにする。互いに能力を共有しない2路線があるのを理想とし、
  難しければ一部を共有する路線（例：{A, B} と {A, C, D}）も許す
- 最少 pt の解の数は問わない。最少 pt を詰めるのはクリアした後のやり込みで、解き方の幅は路線で持たせる
- 配布 pt は、主な路線に寄り道を1つ以上許す量にする。配布 pt を増やすと、その pt でちょうど届く路線も増えるので、
  すべての路線に余裕を持たせることは目標にしない
- お題は、最少 pt の小さい順に並べる

### 路線の書き方

`src/data/<キャラID>/challenges.js` の敵ごとのコメントに、敵の型と、主な路線を書く。
お題の `minimumPoints` には、`verify.js` が出す最少クリア pt を書く。
`tests/data.test.js` が総当たりの結果と突き合わせるので、ツリーやお題を調整して変わったら書き直す。
配布 pt のコメントには、主な路線の最少 pt と、許す寄り道の数を書く。
数値が仮のお題は、その旨をコメントに書き、調整したら外す。
公開版に出さないお題には `debugOnly: true` を付ける（[8. 開発用の表示](#8-開発用の表示debug)）。

### クリアの記録

画面でクリアしたら、使った pt で自己ベストを更新し、お題ごとに保存する（`core/clear-record.js`）。

- **クリアの判定。** 「挑戦」で全員に勝ったとき、連戦は最後の1体を倒したとき。
  デバッグ入力での勝利はツリーで組んだビルドではないので、記録しない
- **最少 pt の開示。** キャラの公開版のお題（`debugOnly` 以外）をすべてクリアするまで、最少 pt を伏せる。
  クリアはやさしく、最少 pt はクリアした後のやり込みにするため。
  伏せている間も「MIN ?pt (全クリアで表示)」と出し、先に目標があることを伝える。
  記録は残り pt と同じ行に出すので、スマホの幅で1行に収まるよう、自己ベストを `BEST`、最少 pt を `MIN` と短く書く
- **★。** 開示した後、自己ベストが最少 pt と同じお題に付ける。開示前に付けると、★の有無で最少 pt が分かってしまう
- **記録を捨てる条件。** 記録した時点の最少 pt を一緒に保存し、今の `minimumPoints` と違えば記録を使わない。
  お題の調整で、古い記録に★が付いたままにならないようにするため。
  使わない記録は消さず、次のクリアで上書きする

## 7. キャラの足し方

キャラは、ツリーとお題を1組ずつ持つ。
`main.js`・`scripts/verify.js`・`tests/data.test.js` は `CHARACTERS` を通してだけツリーとお題を受け取るので、
キャラを足すときにこれらは変えない。

1. `src/data/<キャラID>/` に `tree.js`（`TREE`）と `challenges.js`（`CHALLENGES`）を置く。
   ID は保存キーに使うので、`:` を含めない（`tests/data.test.js` で確かめる）
2. `src/data/characters.js` の `CHARACTERS` に1行足す。並び順が選択肢の順になり、先頭が既定のキャラになる
3. 別のキャラの敵を使うときは、その `challenges.js` で敵の定義を export し、import してお題を組む。
   お題そのものは共有しない
4. `node --test` でツリー・お題の不変条件を、`scripts/verify.js` でお題の解を、キャラごとに確かめる
5. キャラの中身に依存するテスト（ノードの数など）を足すときは、`tests/data.test.js` でキャラの ID を指定して書く
6. キャラが1体のあいだは、キャラの選択欄を出していない。2体目を足すと選択欄が出るので、README の遊び方と保存の説明にキャラの選択を書き戻す

## 8. 開発用の表示（`?debug`）

URL に `?debug` を付けて開いたときだけ、次のものを出す。README は遊ぶ人向けなので、ここにだけ書く。

- `debugOnly: true` を付けたお題。今は数値が仮の連戦（`gauntlet`）
- デバッグ入力

付けずに開くと、`main.js` が `debugOnly` のお題を外したキャラ一覧を作り、以降の選択・保存の読み込みはその一覧を通す。
保存した選択が開発用のお題でも、無いお題として先頭のお題から始まる。
保存キーは変えないので、`?debug` を付けて開き直せば、開発用のお題のビルドも残っている。

### デバッグ入力

画面の「デバッグ入力」を開くと、ツリーを介さずに、能力を文字列で指定して戦闘できる。
選んでいるお題の敵に対して戦い、ログと勝敗は「挑戦」と同じ形で出る。ツリーのビルドには影響しない。

- 能力をカンマ区切りで並べる。例：`HP100,ATK50,DEF10,Poison5,Fire`
- 周期スキル（属性・`Charge`・`Burst`）は、並び順がそのままローテーションの順になる。`HP` `ATK` `DEF` を複数書くと合算する
- 引数を省くと規定値になる。引数が複数ある能力は `:` で区切る。例：`Multi2:0.5`。
  属性（`Physical` `Fire` `Ice` `Thunder`）と `Endure` `Pierce` は引数を取らない
- 引数は0以上の数値。`Multi` の回数は1〜100の整数、`Tempo` のターンの間隔は1以上の整数、`Drain` の割合は0より大きい
- 語の大文字小文字は区別しない。能力のボタンを押すと、規定値つきの1語が末尾に足される。
  ただし `HP` `ATK` `DEF` のボタンは、同じステータスの語があれば最後の語の値に足す（`HP100,ATK10` で `HP+10` を押すと `HP110,ATK10`）
- 書式が不正なときは戦闘を回さず、不正な語と理由を表示する
- 「初期化」で、最初の値（`HP100,ATK10`。ツリーの起点と同じ）に戻す

指定できる能力の一覧は `src/core/ability-table.js` にある。

### 連戦のお題の遊び方

連戦を公開版に出すときは、次の説明を README の遊び方・ルールに戻す。

- 遊び方：連戦のお題では、「挑戦」の代わりに、戦うボスを選ぶボタンが並ぶ
- ルール：「連戦」のお題は、ボスを1体ずつ好きな順に倒していく。
  倒したボスの報酬（HP・攻撃などの能力）は、pt を使わずに自分の能力へ足される。
  1戦でも戦ったらビルドは変えられず、負けたら次の相手を選び直すか、「1体目からやり直す」を押す。
  連戦の途中経過は保存されない

## 9. 設計判断の記録

- **乱数を使わない。** 負けた理由をログから読んで組み直せるようにし、総当たりで解を確かめられるようにするため
- **敵と味方で同じ能力の定義・同じ集計を使う。** 能力の効き方が両者でずれないようにし、能力を1回足せば両方で使えるようにするため
- **`CombatantProfile` を戦闘中に書き換えない。** 戦闘中に変わる HP・食いしばりの使用済みは `Fighter` に分ける。
  総当たりや複数の敵との戦闘で、集計を使い回せるようにするため
- **`clearsChallenge` は1体に負けた時点で打ち切る。** 総当たりで何度も呼ぶため。
  結果の画面では敵ごとの勝敗を並べるので、全員分を返す `simulateChallenge` を別に持つ
- **連戦は、勝敗が「ビルドの集合」だけで決まる前提を崩さない。**
  順番は解の一部になるが、`clearsChallenge` は全順列を試して「勝てる順番が1つでもあるか」を返す。
  連戦の進行（倒した順・報酬）は画面のメモリだけで持ち、保存するのはビルドだけにする
- **連戦は、1戦でも戦ったらビルドを変えられない。** 途中で組み直せると、各戦闘を単体のお題として解けてしまうため。
  変えるには1体目からやり直す
- **報酬は敵の `abilities` とは別に、`reward` として持つ。** 敵の強さと、報酬としての強さを別々に調整するため
- **型は `src/types.d.ts` に集約する。** 独立リポジトリへ移すとき、`.ts` へ機械的に移せるようにするため
- **保存キーは `skill-tree-puzzle:` で始める。** Pages のオリジンを daily-coding の全プロダクトで共有するため
- **キャラごとのデータは `skill-tree-puzzle:<キャラID>:` の下に保存する。**
  選んだお題は `…:<キャラID>:challenge`、ビルドは `…:<キャラID>:build:<お題ID>`。
  キャラを含めないと、別キャラのツリーでビルドを復元しようとして invalid になるため。
  選んだキャラだけは、キャラの外の `skill-tree-puzzle:character` に置く。
  キャラを入れる前のキー（`skill-tree-puzzle:challenge`・`skill-tree-puzzle:build:<お題ID>`）は読まず、ビルドは引き継がない
- **クリアの記録は `…:<キャラID>:record:<お題ID>` に保存する。** 値は自己ベストと、記録した時点の最少 pt
- **最少 pt を開示したかは保存せず、記録から毎回判定する。** 状態の持ち場を記録の1か所にするため。
  お題を足したり、記録を捨てたりすると、再び伏せられる
- **保存できない環境では、クリアしても記録を出さない。** 記録はメモリに持たず、保存だけを読む。
  画面とキャラの解放（#102）が同じ記録を見るようにするため
- **お題はキャラ専用にする。** 同じ敵を複数のキャラで使うときは、お題ではなく敵の定義を共有する。
  配布 pt や路線はツリーによって変わるため
- **今のツリーで組めない保存ビルドは、丸ごと捨てる。** ツリーの調整後に、意図しない形のビルドが残らないようにするため
- **import・CSS・リンクは相対パスで書く。** GitHub Pages ではサブパスで配信されるため
- **`_` で始まるファイル名・フォルダ名を使わない。** Pages は Jekyll を通し、`_` で始まるものを配信しないため
- **データは `.json` ではなく、定数を export する `.js` にする。**
  JSON の import attributes は古い iOS Safari で動かず、fetch だと非同期の初期化が要るため
- **開発用のお題は、ID ではなくデータの `debugOnly` で印付けする。** お題を足すたびに `main.js` を変えずに済むようにするため。
  公開版で選べるお題が1つ以上あることは `tests/data.test.js` で確かめる
